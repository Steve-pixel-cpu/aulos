## 一、架构与整体设计

### Q1：介绍一下你的项目

**要点**：本地 AI 编程 Agent → CLI + 桌面双形态 → 核心是 Agent 自主工具循环 → 规模数字（38k 行内核 / 1316 测试 / 32 个版本）→ 一句差异化（不绑定官方 API，兼容 Anthropic/OpenAI 双协议；92% 重写/新增，不是套壳）。

**追问预案**：和直接调 API 写脚本的区别？→ 工具循环、上下文管理、权限安全、可测试性四层工程。

详见：[01-project-overview.md](01-project-overview.md)

### Q2：整体架构是怎样的？为什么这样分层？

**要点**：CLI / Tauri 桌面壳 → FastAPI（REST + WebSocket）→ runtime 内核 → 工具/权限/压缩/存储。两个关键决策：
- 内核同步、Web 层异步，靠代理桥接（Q4）；
- 根目录只留 shim 入口（evals 和打包脚本硬编码根路径，这是部署约束反推的结构设计）。

**追问预案**：为什么内核不放 FastAPI 里？→ CLI 和桌面两个宿主共用同一内核，内核不能依赖任何宿主框架。

详见：[01-project-overview.md](01-project-overview.md) 第 3 节

## 二、并发与可靠性

### Q3：Agent 循环怎么保证不被打断搞坏？

**要点**：「一致点」概念——所有打断/收束/预算检查都落在「消息已落定」的位置，协议层面保证不留悬空 tool_use（没有 tool_result 的 tool_use 会让下一轮 API 请求直接被拒）。预算耗尽把原因写进历史而不是静默掐断。

**追问预案**：为什么不能直接 try/except？→ 异常处理是事后补救，一致点是事前约定合法状态集；前者永远覆盖不全所有中断路径。

详见：[02-tech-highlights.md](02-tech-highlights.md) 第 1 节

### Q4：同步代码怎么和异步 Web 层共存的？

**要点**：不重写内核。事件循环线程管 WS 收发，工作线程跑同步 `run_turn`；三个代理对象在事件发生处镜像（包住模型客户端镜像 SSE、包住工具注册表镜像开始/结束、包住权限提示器镜像审批）——内核零改动，CLI/Web 双宿主零分叉。

**追问预案**：跨线程怎么通知？→ `loop.call_soon_threadsafe` 塞 asyncio.Queue，sender 协程专职消费；权限审批回传走阻塞的 queue.Queue。

详见：[02-tech-highlights.md](02-tech-highlights.md) 第 2 节

### Q5：讲一个你解决的并发 bug

**首选**：并行 edit 竞态静默吞编辑（案例 C）——两个 edit_file 同文件，后写者整文件覆盖先写者，无任何报错。
**排查叙事**：注入 50ms 延迟放大读-改-写窗口 → 确定性复现 → 按路径加锁 + 锁内刷新缓存 → 双面回归（新行为 + 旧行为不回归）。

**备选**：contextvars 并发崩溃（案例 F）——Barrier 强制真并发的测试技巧；或 spawn 顺序依赖（案例 A）——两层根因的二分定位。

详见：[03-problem-solving-cases.md](03-problem-solving-cases.md) 案例 A/C/F

## 三、上下文工程（AI 应用核心)

### Q6：长对话怎么不爆上下文窗口？

**要点**：三层递进压缩——字符串占位替换（零成本）→ 后台滚动摘要（失败指针不动下轮重试）→ LLM 整段压缩（与滚动摘要重叠区复用）。触发阈值 750k = 1M 窗口的 75%，余量是给输出 token 留的。

**追问预案**：怎么知道用了多少 token？→ CJK 分桶估算（len//4 低估中文 3~4 倍，全局 //2 高估英文 2 倍，分桶是唯一正解）。

详见：[02-tech-highlights.md](02-tech-highlights.md) 第 3 节

### Q7：LLM 摘要有损，怎么防止信息越压越丢？

**要点**：这是本项目的亮点题。三个机制：
1. 机械锚点——归档区锚点由代码从原文抽取、永不经过模型改写，作为摘要出错时的忠实底座（多代接力误差单调累积，必须有不经模型的真值）；
2. 熔断降级——LLM 摘要连续失败自动转规则摘要，压缩链路永不断供；
3. 重复读取去重 + 超长输出落盘按需取，从源头减少进上下文的垃圾。

详见：[02-tech-highlights.md](02-tech-highlights.md) 第 3 节

### Q8：Agent 陷入死循环/无限委派怎么办？

**要点**：多层护栏——委派预算（子 Agent 白名单无派生工具，机制上防套娃）、同一只读操作第 3 次拒止、软 nudge 收束提醒（每回合至多一次）、重读去重指纹（contextvar 跨线程传递）。

**追问预案**：contextvar 跨线程有什么坑？→ 必须在 turn 线程上 set——并行批次由 copy_context() 快照携带，在创建线程上 set 池线程看不见。

详见：[02-tech-highlights.md](02-tech-highlights.md) 第 5 节

## 四、质量保障

### Q9：这种非确定性的系统怎么测试？

**要点**：四层体系——1316 个单元测试（xdist 并行 30 秒）→ 前端 jsdom + Playwright 双层回归 → Agent 级评测（subprocess 拉真实入口 + 确定性检查与 LLM 评委双重判分 + 基线回归）→ CI 退出码门槛。关键设计：evals 不 import 被测代码，「测的是用户实际拿到的东西」；`file_unchanged` 检查防 Agent 改测试凑绿。

**追问预案**：LLM 评委可靠吗？→ 与确定性检查取交集而非替代；基线对比解决评委间漂移。

详见：[02-tech-highlights.md](02-tech-highlights.md) 第 8 节

### Q10：测试怎么避免碰用户真实环境？

**要点**：真实事故驱动的三条 autouse fixture——掐断真实供应商连接（真实事故：泄漏线程拿用户额度打真网，账户莫名 1302 限流）、隔离 settings（真实事故：用户 MCP 配置混进共享工具集，「只在配了 MCP 的机器上翻车」）、隔离数据目录。

**金句**：测试永远不碰用户的真实配置与真实额度——这条纪律是两次真实事故换来的。

详见：[03-problem-solving-cases.md](03-problem-solving-cases.md) 案例后的方法论总结

### Q11：你们怎么保证 bug 修了不再犯？

**要点**：回归钉文化——每个真 bug 留最小复现测试，docstring 带事故日期和根因（如「回归 20261030：显示 A 调用 B」）；双面回归（新行为 + 旧行为不回归）；陷阱文档化进 AGENTS.md；行为级变化走 evals 基线。

**加分项**：展示事故处理闭环全图（见 03 文档末尾），强调「排查方法论」沉淀：排除本次改动（git stash 对照）→ 干净进程模拟 → 二分定位 → 最小复现 → 分层修复。

详见：[03-problem-solving-cases.md](03-problem-solving-cases.md)

## 五、发布工程

### Q12：为什么从 Electron 迁到 Tauri？

**要点**：133MB → 28MB；Tauri 用系统 WebView2；换来原生通知/单实例/自动更新/多窗口。关键加分点：**迁移有回退路径**（Electron 保留为可选打包目标，不删除）；两壳进程模型逐条对齐（令牌门禁、端口避让、探活防误判、复用语义）。

**追问预案**：系统 WebView 版本差异怎么办？→ 承认代价（放弃自带 Chromium 的确定性），但产品形态可控（桌面端用户环境收敛）。

详见：[04-engineering-decisions.md](04-engineering-decisions.md) 1.1

### Q13：跨平台发布踩过什么坑？

**要点**：统一模式「探测 → 降级 → 可观测 → 逃生口」——Wayland 不允许置顶自动切 x11（决策进 boot.log，留环境变量逃生口）；VMware 无 3D 加速自动回退渲染器；缺 GStreamer 播放前主动探测、不可用自动停用不卡死。

**金句**：跨平台发布的一半工作量在环境探测和自动降级；发版链路还要专门记录静默失败模式（签名缺失「构建成功但无 .sig」、latest.json 断链）。

详见：[03-problem-solving-cases.md](03-problem-solving-cases.md) 案例 H

### Q14：打包分发有什么坑？

**要点**：两个事故级细节——PyInstaller 入口双执行自举（`__main__` 执行时被 import 再执行一遍，两份模块副本状态分裂，v5.1.0 打包版启动即崩）；AppImage 的 `_MEIxxx` 环境变量污染导致子进程库解析崩溃。

详见：[03-problem-solving-cases.md](03-problem-solving-cases.md) 案例 G

## 六、开放题

### Q15：这个项目里你最自豪的一个设计？

**推荐答案**（任选其一，按面试官背景适配）：
- **偏系统**：fsatomic——「数据凭空消失」级别 bug 的根因（固定名临时文件多线程互踩）与解法（唯一临时名 + 退避覆盖杀软窗口），Windows 平台工程深度的证明；
- **偏 AI**：摘要漂移对冲——意识到 LLM 摘要多代接力的误差单调累积，用「代码机械抽取、永不经过模型」的锚点做真值底座，这是对「模型不可信」的工程化防御；
- **偏质量**：evals 框架——把「测非确定性系统」这个行业难题落成了 subprocess 真实入口 + 双重判分 + 基线回归的完整方案。

### Q16：如果重做一次，你会改什么？

**参考方向**（展示反思能力，任选 2 个展开）：
- 更早建立 evals 基线——它是后期才补的，之前多个行为回归只能靠人肉发现；
- contextvar/全局状态的清理契约应该从第一天就有——案例 A 那类「两层雷」本质是早期欠债；
- 前端更早拆分——app.js 网状耦合核心「待测试更厚再拆」是理性决策，但如果有重来机会，会在功能铺量期就按域拆。
